# Phase 6 AI Tutor Architecture Contract

**Status: FROZEN for implementation planning; no Phase 6 behavior is implemented yet.** This contract applies Product PRD v0.3 and Python MVP Implementation PRD v0.1 to the existing Attempt, deterministic evaluation, LearningEvent, and SkillState architecture. The ignored `docs/research/ai-tutor/` proposals supply design context; this tracked contract and the explicit user decisions resolve their conflicting clauses.

Labels below distinguish **PRD REQUIREMENT**, **ACCEPTED ARCHITECTURAL JUDGMENT**, **INITIAL IMPLEMENTATION CHOICE**, **CONFIGURABLE MVP DEFAULT**, and **DEFERRED**.

## Scope and authority

- **PRD REQUIREMENT:** Phase 6 supplies a replaceable LLM boundary, one provider, structured tutor responses, mistake and reasoning diagnosis, evidence-based explanation, a six-level hint ladder, and a post-attempt understanding check. Code explanation, conceptual clarification, and personalized feedback are delivered through the diagnosis, hint, and post-attempt explanation responses; they do not require separate public routes. Deterministic execution/evaluation determines correctness. The tutor receives structured, learner-scoped context, not a chat-history dump.
- **ACCEPTED ARCHITECTURAL JUDGMENT:** `TutorService` assembles allowlisted context and validates output. A typed `TutorProvider` has `diagnose_attempt`, `analyze_reasoning`, `generate_hint`, `generate_post_attempt_explanation`, and `evaluate_understanding` operations with provider-independent typed requests/results. Providers have no database access. `MockTutorProvider` serves normal tests; `FallbackHintProvider` supplies only deterministic hint content and does not implement `TutorProvider`.
- **INITIAL IMPLEMENTATION CHOICE:** `GeminiTutorProvider` uses `google-genai`. The model ID is configuration, initially defaulting to `gemini-3.8-flash`; neither `TutorService` nor routes hardcode it. Provider, SDK, and model may be replaced without changing evidence, execution, evaluation, or learner-state contracts. Never configure retired `gemini-2.0-flash` or the legacy `google-generativeai` SDK.
- **CONFIGURABLE MVP DEFAULT:** Level 6 requires a previously delivered Level 5 hint in the same Attempt. The application decides the permitted level; the provider only generates content for that level. Provider retry/timeout and invocation limits are configuration, not product truths.
- **DEFERRED:** Adaptive recommendations, RAG, MCP, fine-tuning, local-model infrastructure, Redis/Kafka/queues, advanced multi-turn agents, and a separate unrestricted final-solution generator. Level 6 itself remains in scope and may give a full explanation/solution when the gate permits it.

## Safe context and authority boundary

Build a bounded request from the current learner's Problem, Attempt, relevant `REASONING_RECORDED` evidence, own Submission code, safe `SUBMISSION_EVALUATED` aggregate status/counts, selected Skill/SkillState context, and prior hint levels. Learner code and reasoning are sensitive; send only the fields needed for the requested task. Never send hidden test input/expected output, hidden or protected stdout/stderr/compile details, Judge0 tokens, secrets, full ORM objects, or another learner's data. Treat code and reasoning as untrusted prompt content.

`ExecutionProvider` executes code in isolation; `EvaluationService` determines test correctness; Attempt/LearningEvent services own lifecycle and historical appends; the learner-state service owns deterministic projections. Tutor output is advisory. It cannot execute learner code, override evaluation, mutate committed events, calculate mastery, directly modify `SkillState`, or block submission/evaluation/Attempt closure. `mastery_probability` never changes because of a tutor flow.

## Public API contract

All request IDs are positive; every client `idempotency_key` is required, nonempty, and bounded to the existing event-key limit. Keys are scoped to the Attempt and action; reusing a key with different target or payload is `409`. Matching retries return the committed result without appending another event. Separate events within one operation use separate deterministic internal identities derived from that action and client key, within the existing key length. Event appends use the Attempt row lock and `attempt_sequence`. Provider failure adds no AI-output event; the learner's separately committed hint request or understanding answer remains. Recheck required Attempt state before appending provider output after a remote call. Every successful route returns `200` with an explicit allowlisted response; internal labels, confidence, provenance, keys, and provider diagnostics are omitted unless a field is explicitly listed below. Missing Attempt/reference is `404`; invalid field values are `422`; ownership/lifecycle/gate/key conflicts are `409`.

**ACCEPTED ARCHITECTURAL JUDGMENT:** The public field names below are the complete Phase 6 v1 response shapes. `diagnosis_summary`, `feedback_text`, `explanation_text`, `key_insight`, `hint_text`, and `question` are nonempty strings; `answer_text` is 1–20,000 characters. `reasoning_quality` is `SOUND`, `PARTIAL`, `FLAWED`, or `UNDETERMINED`; `answer_quality` is `CORRECT`, `PARTIALLY_CORRECT`, `INCORRECT`, or `UNDETERMINED`. These AI assessments are labels, not deterministic code verdicts. `misconception_category` uses the MVP PRD mistake taxonomy (`SYNTAX_ERROR`, `IMPLEMENTATION_ERROR`, `LOGICAL_ERROR`, `CONCEPTUAL_ERROR`, `COMPLEXITY_ERROR`, `EDGE_CASE_ERROR`, `MISREAD_PROBLEM`, `WRONG_PATTERN`, `INCOMPLETE_REASONING`) or is null when no supported mistake is diagnosed. `misconception_label` is optional detail within that category. No model confidence is exposed.

| Method and path | Request fields | Success response fields | Attempt state | Events and idempotency | Provider failure |

For hint retries, returning an already delivered result after Attempt closure is retrieval of the prior operation, not a new hint action. New hint generation and delivery require `ACTIVE`; if the Attempt closes during generation, do not deliver or append `HINT_DELIVERED`. A gate rejection is `409`; its valid `HINT_REQUESTED` remains. The gate reads *delivered* prior Level 5 evidence and its versioned policy, not merely earlier requests. Level 6 may include the PRD's full explanation/solution only when permitted. No standalone final-solution route is authorized.

The deterministic understanding question asks the learner to explain why the final approach works, its time/space complexity, and one edge case. For a `GAVE_UP` Attempt, the versioned wording asks what would need to change in the attempted approach rather than asserting it worked. `PROMPTED` and `ANSWERED` are distinct immutable events. The answer evaluation is an AI interpretation, not objective correctness or mastery evidence.

## Event payload and provenance contract

`LearningEvent.evidence` records objective actions and content actually delivered/received. `derived_labels` holds AI classifications, answer/reasoning quality, and any retained model confidence. `provenance` identifies source, provider, model ID, prompt/schema/policy versions, invocation/request ID, and relevant generation configuration. Confidence is **not** provenance and is never `mastery_probability`. No undelivered generated text is stored as learner interaction evidence. Committed events are append-only; a later correction appends history rather than editing a prior row.

| Event type | Evidence | Derived labels | Provenance |
|---|---|---|---|
| `HINT_REQUESTED` (existing) | Requested level and action context | None | Learner source and request policy/version |
| `HINT_DELIVERED` (existing) | Request event ID, delivered level, stable content ID, exact hint text delivered | None | Model identity/prompt/gate versions, or deterministic fallback rule/version |
| `TUTOR_DIAGNOSIS_GENERATED` (new) | Submission ID, deterministic status, exact diagnosis text delivered | Misconception category/label and optional confidence | Model/provider/prompt/schema/invocation and source event IDs |
| `TUTOR_REASONING_ANALYSIS_GENERATED` (new) | Source reasoning event ID and exact feedback delivered | Reasoning quality/gaps and optional confidence | Model/provider/prompt/schema/invocation |
| `POST_ATTEMPT_EXPLANATION_GENERATED` (new) | Exact explanation and key insight delivered | Optional interpretation only | Model/provider/prompt/schema/invocation |
| `UNDERSTANDING_CHECK` (existing), `PROMPTED` | Deterministic question and question version | None | Deterministic rule/version |
| `UNDERSTANDING_CHECK` (existing), `ANSWERED` | Prompt event ID and exact learner answer | None | Learner source |
| `TUTOR_UNDERSTANDING_EVALUATED` (new) | Prompt/answer event IDs and exact feedback delivered | Answer quality and optional confidence | Model/provider/prompt/schema/invocation |

New type values fit the existing `LearningEvent.event_type` `VARCHAR(40)`. The existing JSONB evidence/labels/provenance fields, event ordering, and idempotency indexes support this scope; **no Phase 6 migration or revision 0006 is authorized**. The current Alembic head remains `20260929_0005`. Future learner-facing event serialization must explicitly allowlist every new type and only safe evidence fields.

## Failure, projection, and verification boundary

Hints use safe deterministic fallback only for hint content; it is not a diagnosis or full `TutorProvider`. Diagnosis, reasoning analysis, post-attempt explanation, and understanding evaluation return `503` after configured provider retries. They never create synthetic successful tutor events. A failed understanding evaluation preserves the learner's answer; a failed hint delivery preserves the request. Provider failures never block existing submission, execution, evaluation, Attempt lifecycle, LearningEvent history, or mastery flows.

If Phase 6 populates `SkillState.recent_error_types`, it must deterministically replay committed diagnosis events under a versioned label/projection rule. No provider directly changes any SkillState field. If clean replay cannot be achieved in scope, defer that field rather than use an imperative shortcut. BKT, binary observation eligibility, and `mastery_probability` remain unchanged.

Normal tests use `MockTutorProvider`, isolated provider failures, and no live LLM/Judge0. Verify every route's ownership, status, idempotency, event causality, request-without-delivery recovery, answer-without-evaluation recovery, Level 6 gate, privacy allowlists, immutable source events, and unaffected deterministic/BKT regression behavior before Phase 6 implementation is considered complete.
